# 창작 과정 증명 설계 (2026-10-02, 1~5단계 구현 2026-10-03, 저장 묶음·달별 조각 2026-10-03)

작가가 "이 작품을 내가 이렇게 써 왔다"는 것을 남에게 보여 줄 수 있게 한다. 앱이 쓰는 과정을 조용히 기록해 두었다가, 필요할 때 **창작 과정 증명서**로 묶어 낸다. 배경과 수익 연결은 [revenue-ai-report.md](revenue-ai-report.md), [business-model.md](business-model.md).

## 1. 왜 필요한가

| 상황 | 지금 | 증명서가 하는 일 |
|---|---|---|
| 플랫폼이 창작 경위를 물을 때 | 카카오엔터는 심사 중 의심이 들면 작가·CP에 저작권 소명을 요청한다(2026-09). 지금은 작가가 내밀 자료가 없다 | 몇 달에 걸쳐 고쳐 쓴 흐름, 날짜별 분량, 초고와 최종본의 차이를 자료로 낸다. 판단은 플랫폼이 한다 |
| 공모전 | 창작 경위를 물을 때 낼 자료가 없다 | 출품작 하나의 창작 과정을 첨부한다 |
| 표절·선후 분쟁 | "내가 먼저 썼다"를 증명하기 어렵다 | 그 내용이 그 날짜에 이미 있었음을 시각 인증으로 보인다 |
| 출판 계약·저작권 등록 | 창작 경위를 설명할 자료가 없다 | 창작 경위 자료로 쓴다 |

## 2. 증명하는 것과 하지 않는 것

**AI를 썼는지 안 썼는지는 다루지 않는다** (2026-10-02 결정). AI 글을 보며 옮겨 치거나 다른 앱에서 AI를 쓴 것은 기술로 가려낼 수 없다. 할 수 없는 것을 증명하는 척하면 증명서 전체의 신뢰를 잃는다. 증명서는 사실만 보인다.

| 보이는 것 (사실) | 다루지 않는 것 |
|---|---|
| 어떤 내용이 **늦어도 그 시각에** 있었다 (시각 인증) | AI를 썼는지, 안 썼는지 |
| 기록이 **나중에 고쳐지거나 빠지지 않았다** (해시 사슬) | 글의 품질이나 독창성 |
| 작품이 어떤 흐름으로 쓰이고 고쳐졌다 (날짜별 분량, 고친 횟수, 붙여넣기, 가져온 파일) | 기록을 켜기 전의 과정 |

증명서와 앱 안내에도 "이 증명서는 창작 과정의 기록이며 AI 사용 여부를 판단하지 않습니다"라고 적는다. 그 자료로 무엇을 판단할지는 읽는 사람(플랫폼, 심사위원, 법원)의 몫이다.

## 3. 기록하는 것: 창작 일지

원고 내용은 일지에 넣지 않는다. 키 하나하나의 입력도 기록하지 않는다(감시처럼 느껴지고, 증명에 꼭 필요하지 않다).

| 항목 | 언제 | 남기는 것 | 원고 내용 |
|---|---|---|---|
| 저장 | 회차를 저장할 때 (이미 자동 저장됨). 같은 회차를 10분 안에 저장한 것은 한 줄로 묶음 | 회차 아이디, 시각, 본문 지문(SHA-256), 글자 수, 늘어난·줄어든 글자 수, 묶은 저장 횟수와 첫 저장 시각, 기기 | 없음 |
| 쓰기 묶음 | 쓰기를 시작하고 5분 넘게 쉴 때까지 | 시작·끝 시각, 넣은 글자 수, 지운 글자 수 | 없음 |
| 붙여넣기 | 100자 이상 붙여 넣을 때 | 글자 수, 앱 안에서 옮긴 것인지 밖에서 온 것인지 | 없음 |
| 가져오기 | txt·docx·한글 파일을 가져올 때 | 파일 이름, 파일 지문, 만든 회차 | 없음 |
| 기록(스냅샷) | 기록이 만들어질 때 | 기록 지문, 종류 | 없음 (기록 파일 자체는 기존대로 기기에) |
| 교정 주고받기 | 원고를 보내고, 교정본을 받고, 교정을 반영할 때 | 보낸 파일·원고 지문, 받은 파일 지문, 반영한 뒤 본문 지문 | 없음 |
| 시각 고정 | 하루 한 번 (아래 4장) | 고정한 지문, 시각 인증 응답 | 없음 |

- 가져온 원고는 "밖에서 쓴 글"로 구분된다. 한글에서 쓰던 작가가 옮겨 와도 불리하지 않도록, 가져온 파일의 지문과 날짜를 남기고 증명서에 "○○.hwpx에서 가져옴"으로 보인다.
- 앱 안에서 회차끼리 잘라 붙인 것은 바깥 붙여넣기로 치지 않는다.
- 이 앱의 AI 기능(설정 점검, 요약, AI 독자 등) 사용은 일지에 넣지 않는다. AI 여부를 다루지 않는다는 원칙과 맞추고, 원고를 고치지 않는 점검 기능이 "AI 사용"으로 오해받지 않게 한다.

## 4. 위조를 막는 방법

### 4.1 해시 사슬

- 일지 한 줄마다 앞 줄의 지문을 담는다. 중간 줄을 고치거나 빼면 그 뒤의 사슬이 모두 깨진다.
- 기기마다 따로, 달마다 나눠 쓴다: `<작품>/.journal/<기기 아이디>/<YYYY-MM>.jsonl`. 새 달 첫 줄은 지난 조각 마지막 줄의 지문을 담아 사슬이 파일을 넘어 이어진다. 2026-10 이전 판이 쓴 `<기기 아이디>.jsonl`은 그대로 두고 첫 조각으로 읽는다. 외부 드라이브 동기화로 다른 기기의 일지도 함께 오지만 같은 파일을 두 기기가 고치지 않으므로 충돌이 없고, 지난 달 조각은 바뀌지 않아 다시 올라가지 않는다.
- 일지는 덧붙이기만 한다. 앱이 지우지 않는다(작품을 완전히 지울 때만 함께 지움).

### 4.2 시각 고정 (시각 인증)

- 하루 한 번(인터넷이 될 때), 그날 모든 기기 일지의 마지막 지문과 각 회차의 본문 지문을 하나로 묶은 지문(머클 루트, 32바이트)을 **공개 시각 인증 기관(TSA, RFC 3161)**에 보낸다. 돌아온 서명된 시각 인증 토큰을 `.journal/anchors/`에 저장한다.
- 원고는 보내지 않는다. 지문 32바이트만 간다. 그 지문으로는 원고를 되살릴 수 없다.
- 인증 기관은 둘 이상에 함께 맡긴다(한 곳이 사라져도 검증되게). 무료로 쓸 수 있는 공개 TSA를 기본으로 하고, 이용 조건(자동 요청 허용, 횟수)을 출시 전에 확인한다.
- 효과: 기기 시계를 돌려 과거 날짜로 일지를 만들어도, 시각 인증과 맞지 않아 드러난다. "그 날짜에 이 내용이 있었다"는 제3자의 서명으로 증명된다.
- 선택: 법적 효력을 더 원하는 작가를 위해 국내 공인 시점확인 서비스를 유료 옵션으로 검토한다(법률 검토 필요).

### 4.3 증명용 기록 보관

- 자동 기록은 90일이 지나면 지워진다(`snapshot::prune`). 지문과 일지는 남으므로 "그때 이런 지문의 내용이 있었다"는 증명은 계속된다. 하지만 그때의 **실제 내용**을 보여 주려면 기록 파일이 있어야 한다.
- 설정 "창작 과정 보관": 켜면 회차마다 **하루 마지막 상태 하나씩**을 지우지 않고 남긴다. 장편이라도 압축하면 크지 않지만, 작품 크기 표시([drive-apps.md](drive-apps.md) "드라이브 공간")에서 따로 보인다.

### 4.4 남는 한계

- 일지를 켜기 전, 다른 앱에서 쓴 부분은 "가져옴"으로만 보인다.
- 기기를 잃고 동기화도 하지 않았다면 일지도 사라진다. 외부 드라이브나 작가 플랜 동기화로 일지가 함께 보관된다.
- 저장 줄은 10분씩 묶어 쓰므로, 앱이 갑자기 꺼지면 마지막 묶음(최대 10분)의 일지 줄이 빠질 수 있다. 원고는 이미 저장되어 있다. 작품을 닫거나 앱을 정상으로 끄면 빠지지 않는다.
- 같은 묶음 안 중간 저장의 본문 지문은 남지 않는다(묶음 끝 지문만 남음). 검증 도구가 "이 원고가 일지에 있다"고 찾는 것은 묶음 끝 상태, 기록, 시각 고정, 가져온 파일이다.

## 5. 증명서

### 5.1 모양

- 사람이 읽는 **PDF**(또는 HTML) 한 장짜리 요약 + 여러 쪽의 세부, 그리고 기계가 검증하는 **증명 자료 파일**(`증명자료.json`: 일지, 시각 인증 토큰, 지문 목록)을 하나의 묶음으로 낸다.
- 범위를 고른다: 작품 전체, 일부 회차, 기간. 공모전에는 출품작만.
- 원고 공개 범위를 고른다: 기본은 **원고 내용 없이** 흐름과 지문만. 작가가 고르면 특정 회차의 초고와 최종본 비교 발췌를 넣는다.

### 5.2 내용

1. **요약 문장**: "「달빛 서점의 마지막 손님」 1~40화는 2025년 3월 2일부터 2026년 9월 30일까지 214일 동안 1,312번에 걸쳐 쓰고 고쳤습니다. 바깥에서 붙여 넣은 글은 전체의 2%이고, 1~3화는 '초고.hwpx'에서 가져왔습니다." 끝에 "이 증명서는 창작 과정의 기록이며 AI 사용 여부를 판단하지 않습니다"를 붙인다.
2. **날짜별 분량**: 날마다 넣은 글자·지운 글자. 사람의 쓰기는 들쭉날쭉하고 고치는 양이 많다.
3. **회차별 표**: 처음 쓴 날, 마지막으로 고친 날, 쓰기 묶음 수, 초고 대비 얼마나 고쳤는지(바뀐 비율), 붙여넣기.
4. **고친 흐름**: 고른 회차의 초고 → 중간 → 최종 변화(작가가 공개를 고른 경우만).
5. **가져온 파일과 교정 주고받기**: 날짜, 파일 이름, 지문.
6. **시각 인증 목록**: 날짜, 지문, 인증 기관.
7. **검증 방법**: 아래 6장 안내와 검증 도구 주소.

## 6. 검증

- **누구나 무료로**: 공개한 검증 도구(오픈소스, 브라우저 안에서 계산하는 정적 웹 페이지와 명령줄 도구)에 증명 자료 파일을 넣으면 다음을 확인한다.
  - 해시 사슬이 끊기지 않았는지.
  - 시각 인증 토큰의 서명이 맞는지, 지문이 일지와 맞는지.
  - (원고 파일도 함께 주면) 그 원고의 지문이 기록에 있는지.
- **검증 링크 (작가 플랜)**: 증명서를 우리 서버에 올려 링크로 보낸다. 받는 사람은 링크만 열면 검증 결과를 본다. 서버 비용이 드는 부분이라 유료다.

## 7. 원칙

- 일지는 기기 안에만 있고 기본으로 켜져 있다. 처음 쓸 때 "쓰는 과정을 이 기기에 기록합니다(내용은 기록하지 않음)"를 알리고 끌 수 있게 한다.
- 시각 고정은 인터넷으로 지문을 보내므로 처음 한 번 묻는다.
- 증명서는 작가가 만들 때만 생기고, 무엇을 넣을지 작가가 고른다.

## 8. 무료와 유료

| 부분 | 무료 / 유료 | 이유 |
|---|---|---|
| 창작 일지, 해시 사슬, 시각 고정(공개 TSA), 증명서 PDF, 검증 도구 | 무료 | 기기 안에서 되고 서버 비용이 없다. 작가의 생계를 지키는 기능이라 잠그지 않는다 |
| 검증 링크, 일지·시각 인증의 클라우드 보관 | 작가 플랜 | 우리 서버가 든다 |
| 국내 공인 시점확인 | 건당 실비 | 외부 유료 서비스 |
| 플랫폼·공모전용 일괄 검증 | 기업 상품 | 플랫폼이 제출된 증명서를 대량으로 확인하는 도구 |

## 9. 구현

### 9.1 이미 있는 것

| 있는 것 | 쓰임 |
|---|---|
| `store::on_write` (모든 원자적 저장 뒤에 불리는 고리) | 저장 일지 남기기 |
| `store::sha256`, `DocFile::rev()` | 본문 지문 |
| 기록(`snapshot.rs`, 종류별 기록) | 기록 지문, 증명용 보관 |
| 가져오기(`import/`) | 가져온 파일 지문 |
| 기기 구분(동기화 사본 처리) | 기기별 일지 파일 |
| 외부 드라이브·폴더 동기화 | 일지가 기기 사이에서 함께 보관됨 |

### 9.2 새로 만들 것과 크기

| 단계 | 내용 | 크기 |
|---|---|---|
| 1 | 일지 모듈 (core): 기기별 파일, 해시 사슬, 저장·기록·가져오기 항목 | 1~2주 · **완료** |
| 2 | 편집기에서 쓰기 묶음과 붙여넣기 크기를 보내는 명령 | 1주 · **완료** |
| 3 | 시각 고정: 머클 루트, RFC 3161 요청·응답 저장(RustCrypto `cms`·`x509-tsp` 계열 또는 직접 DER), 오프라인이면 나중에 | 1~2주 · **완료** |
| 4 | 증명서: 범위·공개 고르기 화면, PDF·HTML, 증명 자료 파일 | 2주 · **완료** (HTML, 브라우저에서 PDF로 인쇄) |
| 5 | 검증 도구: 명령줄 + 정적 웹 페이지(같은 Rust 코드를 WebAssembly로) | 1~2주 · **명령줄 완료**, 웹 페이지는 다음 |
| 6 | 검증 링크 (작가 플랜 서버와 함께) | 서버 단계에서 |

1~2단계는 구현했다(2026-10-03). 파일 형식과 동작은 [architecture.md](architecture.md) "창작 일지". 정한 것: 켜고 끄기는 기기 단위(앱 설정 폴더 `journal.json`, 모든 작품에 적용), 작품 설정 기본 정보에서 끈다. 저장 항목의 늘어난·줄어든 글자 수는 저장 직전 디스크 글과의 길이 차이다(실제 넣고 지운 양은 쓰기 묶음에 있음). 되돌리기·모두 바꾸기·사본으로 바꾸기처럼 편집기를 거치지 않고 본문을 바꾸는 일은 저장 항목 없이 그 앞의 기록(`before-restore`, `before-replace`, `before-copy`) 항목으로만 남는다. 교정 주고받기(`exchange`: 보냄·받음·반영, [corrections.md](corrections.md))도 들어갔다(2026-10-03). 시각 고정 `anchor` 줄은 3단계에서 더했다.

3~5단계도 구현했다(2026-10-03). 파일 형식은 [architecture.md](architecture.md) "창작 일지"와 "시각 고정·증명서". 정한 것:

- **시각 고정** (`crates/core/src/anchor/`, 앱 `commands/anchor.rs`): 잎은 기기마다 "마지막 일지 줄(시각 고정 줄 제외)의 지문"과 회차마다 "본문 지문", 이름순. 머클 루트는 RFC 6962 방식(잎 `0x00`, 마디 `0x01` 접두). 요청은 SHA-256, 8바이트 nonce, certReq. 기본 기관은 DigiCert·Sectigo·FreeTSA 셋(셋 다 계정 없이 `application/timestamp-query` POST를 받음, 2026-10-03 확인). 하나라도 서명하면 그날은 끝, 모두 실패하면 한 시간 뒤 다시. 지난번과 지문이 같으면(쓴 것이 없으면) 보내지 않는다. 시각 고정 줄은 잎에 넣지 않아, 고정만으로 다음 날 다시 보낼 일이 생기지 않는다.
- **처음 한 번 묻기**: 일지 알림을 본 뒤 작품을 열 때 "날짜 증명 받기"를 묻는다(받기 / 받지 않기). 기기 설정(`journal.json`의 `anchor`), 작품 설정 창작 일지에서 바꾸고 "지금 받기"로 바로 받을 수 있다.
- **파일 이름**: 명세의 `<날짜>-<기관>.tsr` 대신 `<UTC 시각 도장>-<기기 id>-<기관>.tsr`. 두 기기가 같은 날 고정해도 같은 파일을 쓰지 않게 하려고 기기를 넣었다.
- **응답 확인**: 상태, TSTInfo, CMS 서명(RSA PKCS#1 v1.5 SHA-256/384/512, ECDSA P-256/P-384), 서명 인증서의 시각 인증 용도와 유효 기간, 토큰 안에 든 인증서 사슬의 서명. 최상위 발급자가 믿을 만한지는 판단하지 않고 이름을 보여 준다(루트 목록을 앱에 넣지 않음).
- **창작 과정 보관**: 작품 설정(`project.json`의 `keepDaily`, 기본 꺼짐). 켜면 90일 정리와 "오래된 자동 기록 정리" 모두 회차마다 하루(이 기기 시간대)의 마지막 기록을 남긴다. 작품 크기에 "그중 창작 과정 보관 ○MB"로 보인다.
- **증명서** (`crates/core/src/proof/`, 화면 `ProofDialog.tsx`): 작품 설정 창작 일지의 "창작 과정 증명서 만들기…". 범위(작품 전체 / 회차 고르기 / 기간), 고른 회차의 초고(남은 가장 오래된 기록)와 지금 글 비교(기본 넣지 않음), 시각을 날짜까지만(기본 켜짐). 고른 폴더 안에 `<제목> 창작 과정 증명 <날짜>/` 폴더를 만들어 `창작 과정 증명서.html`(글꼴·스크립트 없이 한 파일, 인쇄하면 PDF)과 `증명자료.json`을 둔다. 증명서를 만들 때 검증 도구와 같은 계산으로 스스로 확인한 결과도 싣는다.
- **증명 자료의 범위**: 일지는 첫 줄부터 기간 끝(또는 기간을 덮는 첫 시각 고정이 가리키는 줄)까지 넣되, 범위 밖 줄은 지문만(`{"hash": …}`) 넣는다. 사슬은 지문으로 이어 확인하고, 내용은 가린다. 시각은 증명 자료에서 가릴 수 없다(사슬과 서명이 그 시각을 보증하므로). "날짜까지만"은 사람이 읽는 증명서에만 적용된다.
- **검증 도구** (`cargo run -p writer-core --example verify_proof -- 증명자료.json [원고 파일 …]`): 사슬, 각 시각 고정의 루트 재계산·토큰 파일 지문·서명·지문 일치, 일지 시각과 시각 인증의 앞뒤(시계를 돌린 기록은 "주의"), 원고 파일 지문의 위치(지금 회차, 저장 기록, 시각 고정, 가져온 파일). 끝에 "AI 사용 여부를 판단하지 않습니다"를 붙인다.
- **다음**: 정적 웹 검증 페이지(같은 `proof::verify`를 WebAssembly로), 앱 안에서 PDF 바로 저장, 인증 기관 루트 인증서 목록으로 사슬 끝까지 확인.

**저장 묶음과 달별 조각** (2026-10-03, [safety-design.md](safety-design.md) S3): 저장마다 줄을 쓰면 한 해 수십~수백 MB가 되고 동기화가 매분 통째로 다시 올려서 바꿨다. 같은 회차를 10분 안에 저장한 것은 `save` 한 줄(`saves` 횟수, `since` 첫 저장 시각, 늘어난·줄어든 글자 수는 합, 본문 지문·글자 수는 마지막 값, `time`은 마지막 저장 시각)이 된다. 다른 회차 저장, 다른 종류 줄, 작품 나가기, 창 닫기·앱 끝, 앱의 1분 점검(10분 넘은 묶음), 증명서·시각 고정 직전에 묶음을 먼저 쓴다. `saves`가 없는 옛 줄은 저장 1번으로 센다(증명서의 "○번에 걸쳐", 일지 요약). 파일은 `.journal/<기기>/<YYYY-MM>.jsonl`(줄 시각의 UTC 달)로 나누고, 옛 단일 파일은 첫 조각으로 둔다. 사슬·증명 자료·시각 고정 잎의 형식은 그대로다(조각을 이은 줄이 예전 한 파일의 줄과 같음).

1~5는 서버 없이 된다. 교정본 기능과 독립이라 언제든 시작할 수 있다. 가능하면 **일지(1~2단계)는 빨리 넣는 것이 좋다.** 기록은 켜진 날부터만 쌓이기 때문이다.

### 9.3 출시 전 확인할 것

- 공개 TSA의 이용 조건(자동 요청, 횟수 제한)과 장기 신뢰성. 2026-10-03에 같은 요청을 받아 준 곳: DigiCert, Sectigo, FreeTSA(기본), SSL.com, GlobalSign, Certum, Entrust, 벨기에 정부(BOSA). Apple(`timestamp.apple.com`)의 토큰은 TSTInfo의 OID가 DER 규칙에 맞지 않아 읽지 못한다.
- 시각 인증 자료의 국내 증거 효력, 공인 시점확인 서비스의 비용(법률 자문).
- 플랫폼(카카오엔터, 리디 등)과 공모전 주최 측이 소명 자료로 받아들일지. 실제 담당자에게 증명서 견본을 보여 주고 의견을 듣는다.
- 개인정보: 쓰기 시각 기록이 생활 패턴을 드러낼 수 있다. 증명서에서 시각을 날짜 단위로만 보이는 선택을 둔다.

# 기능 점검 보고서: 더 있어야 할 것, 보완할 것, 주력 기능의 빈틈 (2026-10-03)

세 갈래로 조사했다. (1) 경쟁 앱 기능 비교(국내 뮤블·노벨라·펜시브·타입탁·서사공방 등, 해외 Scrivener·Dabble·Plottr·Novelcrafter 등), (2) 작가들이 커뮤니티에서 말하는 요구와 불만(DC 웹소설 연재 갤러리, 아카라이브, 브런치, 클리앙 등), (3) 우리 코드의 주력 기능 점검(320회차 140만 자 작품으로 성능 측정 포함). 코드 점검은 2026-10-03 시점이고, 같은 날 다른 작업이 진행 중이라 일부는 이미 고쳐졌을 수 있다.

## 1. 결론 먼저

1. **새 기능보다 먼저 고칠 것이 있다.** 원고를 잃거나 작품이 열리지 않을 수 있는 경로 5곳(3장)과, "한글 대신 쓰는 앱"이라는 약속의 확인(실제 한글 입력기, 실제 한글에서 HWPX 열기)이 아직 안 됐다.
2. **작가 요구 1~3위는 맞춤법, 한글 파일, 플랫폼 글자 수다.** 한글 파일은 이미 강점이다. 맞춤법(특히 인물 이름 같은 고유명사를 빼는 기능)과 플랫폼별 글자 수·붙여넣기 맞추기가 비어 있다. 글자 수 쪽은 작고 효과가 크다.
3. **경쟁 앱이 다 가진데 우리만 없는 것은 "구상 도구"다.** 카드형 플롯보드, 플롯 그리드·타임라인, 인물 관계도, 캔버스. 국내 신생 툴이 모두 이것으로 경쟁한다. 우리는 표(개요 표)만 있다.
4. **우리만의 강점은 분명하다.** 한글·Word 교정본 주고받기, 창작 과정 증명, 원고 서식·원고지 매수, 폴더 동기화 충돌 처리, 내 컴퓨터에 남는 원고. 경쟁 앱은 대부분 클라우드 중심이고 로컬은 뮤블뿐이다.

## 3. 주력 기능의 빈틈 (코드 점검)

### 3.1 먼저 고칠 것 (원고 안전)

| 심각도 | 문제 | 위치 | 고칠 방향 |
|---|---|---|---|
| 높음 | 휴지통 비우기·오래된 기록 정리 중 파일 하나만 못 지워도(동기화 프로그램·백신이 잡고 있을 때) **작품이 열리지 않는다** | `project/overview.rs` (`purge`·`prune`을 `?`로 이어 부름) | 정리는 실패해도 건너뛰고 기록만. 지우기에도 재시도 |
| 높음 | 드라이브 맞추기 중 파일을 잠깐 못 읽으면 "이 기기에서 지움"으로 보고 **드라이브와 다른 기기에서 그 파일을 지운다** | `crates/sync/src/engine.rs` (`scan`의 `continue`, 지우기 경로) | 못 읽은 파일은 "모름"으로 두고 이번 맞추기에서 건너뜀 |
| 높음 | 창작 일지가 저장마다 한 줄(약 280바이트)씩 계속 커진다. 드라이브 맞추기는 이 파일을 1분마다 통째로 다시 올린다 | `journal.rs`, `doc.rs`, `sync/engine.rs`, `store/drives.ts` | 저장 줄을 쓰기 묶음·몇 분 단위로 합치기, 일지를 달마다 파일로 나누기 |
| 중간~높음 | UTF-8이 아닌 회차 파일(메모장 ANSI 저장 등)이 트리·합계·찾기·증명서에서 **아무 알림 없이 빠진다** | `overview.rs`, `search.rs`, `cards.rs`, `proof/facts.rs`, `anchor/mod.rs` | "열 수 없는 회차"로 트리에 표시, EUC-KR로 읽어 고치기 제안 |
| 중간 | project.json이 깨지면 복구할 길이 없고 오류 문장에 영어가 섞인다 | `project/mod.rs` | 저장 때 `project.json.bak`, 읽기 실패 시 백업이나 회차 파일로 구조 다시 만들기 |
| 중간 | 기록 직후 9분 안에 큰 글을 지우면 자동 기록이 남지 않아, 앱이 꺼지면 되살릴 수 없다 | `snapshot.rs`, `doc.rs` (10분 간격) | 저장으로 글이 크게 줄면(500자 이상 또는 20% 이상) 시간과 상관없이 기록 |
| 중간 | 저장 실패 뒤 다시 시도하는 타이머가 없다. 저장 상태가 앱 전체에 하나라 다른 저장 성공이 실패 표시를 덮는다. 메모 저장 실패는 창 닫기를 막지 않는다. 제목·시놉시스 저장이 실패하면 고친 값을 버린다 | `editor/session.ts`, `CardEditor.tsx`, `Notes.tsx`, `DocPane.tsx` | 문서마다 실패 상태, 점점 간격을 늘려 다시 시도, 고친 값 유지 |

### 3.2 약속 확인 (한글 대체)

| 심각도 | 항목 | 메모 |
|---|---|---|
| 높음 | 실제 한글 입력기(MS 한글 IME) 검증 | 조합 중에도 설정집 이름 강조·찾기 강조·들여쓰기 꾸밈이 다시 계산된다. 조합이 깨질 위험. 조합 중에는 미루고 조합이 끝난 뒤 한 번만 계산. 다른 기기 글 불러오기도 조합 중인지 확인 |
| 높음 | 내보낸 HWPX를 실제 한글에서 열기 | 지금은 python-hwpx 검사만 통과 |
| 중간 | 실제 한글·Word 교정본으로 교정본 읽기 확인 | 메모, 형광펜, 문단 끝 추적 |

### 3.3 긴 원고 (측정: 320회차 145만 자, release 빌드)

| 작업 | 시간 |
|---|---|
| 작품 열기(기록 6,400개 포함) | 0.49초 |
| 작품 요약 다시 읽기 | 0.18~0.31초 |
| 회차 하나 열기 | 0.5ms |
| 자동 저장 | 중앙값 9~11ms |
| 작품 전체 찾기 | 0.03~0.15초 |
| 작품 전체 내보내기 (txt·docx·HWPX) | 0.17~0.25초 |

회차 단위로 나뉜 작품은 충분히 빠르다. 문제는 두 가지다.

- **구조를 조금만 바꿔도 작품 전체를 다시 읽는다.** 회차 추가·옮기기, 부 이름 바꾸기, 카드 만들기마다 모든 회차를 읽고 센다(한 번에 약 0.3초, 드라이브 폴더 위에서는 더 느림). 트리는 가상화가 없고 저장마다 다시 그려지며, 사이드바의 작품 전체 글자 수는 쓰는 동안 바뀌지 않는다.
- **회차 하나가 아주 크면 편집기가 느려진다.** 140만 자 한 회차에서 글자 하나 칠 때마다 들여쓰기 꾸밈 0.57초, 설정집 이름 강조 3.2초, 저장 0.26~0.47초. 가져오기에서 "나누지 않기"를 고르면 생길 수 있다. 가져오기에서 큰 회차는 나누라고 권하고, 꾸밈은 바뀐 문단만 다시 계산한다.

### 3.4 그 밖의 보완

- 기록 되돌리기나 모두 바꾸기를 하면 열린 탭 전부의 되돌리기 기록이 사라진다(앱 전체에 버전 하나).
- 설정집 이름 강조에 낱말 경계가 없어 "서하"가 "서하늘" 안에서도 강조된다.
- 내보내기는 회차 하나만 못 읽어도 전체가 실패한다.
- 시험: Rust 185개, 화면 75개 통과. 자동 저장·두 창 맞추기·충돌 다시 불러오기 같은 화면 쪽 데이터 경로에는 시험이 없다. 깨진 project.json, UTF-8이 아닌 회차, 정리 실패, 동기화 읽기 실패, 큰 작품 성능 회귀 시험도 없다. CI는 다른 작업에서 만드는 중이다.

## 5. 쓰는 사람 쪽 빈틈 (사용성)

- 시작 화면에 "기존 원고 가져오기"가 없다. 설계(screens.md)와 다르다. 한글에서 옮겨 오는 작가의 첫 경로가 막힌다.
- ~~단축키 목록·바꾸기 화면이 없다.~~ 목록은 됨(2026-10-03, F1·Ctrl+/·⋯ 메뉴, 키 처리와 같은 표에서 만듦). 바꾸기 화면은 아직.
- 대화상자: Tab 포커스가 밖으로 빠지고, 닫은 뒤 포커스를 돌려주지 않는다. **한글 조합 중 Esc로 조합을 취소하려 하면 창이 닫히고**, 바깥을 누르면 고르던 내용과 함께 닫힌다.
- 큰 작품을 여는 동안 진행 표시가 없다.
